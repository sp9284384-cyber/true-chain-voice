Introduction — Anonymous Reporting of Harassment or Corruption

Omni_CyberTech_15: Anonymous Reporting of Harassment or Corruption
focuses on building a secure digital platform that allows individuals to
report workplace harassment, corruption, misconduct, abuse of authority,
or other sensitive incidents anonymously. The official problem statement
highlights that many such incidents remain unreported because people
fear retaliation or other consequences, creating a need for a secure and
anonymous reporting mechanism.

In many organizations and institutions, victims or witnesses may
hesitate to report wrongdoing because they do not trust existing
complaint systems. Traditional reporting mechanisms often require
personal details such as a name, email address, phone number, employee
ID, or other identifying information. Even when anonymity is promised,
users may still worry that their identity could be discovered through
uploaded documents, images, metadata, IP information, or internal
records. This lack of trust can discourage people from reporting genuine
incidents.

The proposed solution is therefore a privacy-preserving anonymous
reporting platform designed around the principle of "report without
revealing your identity." The platform would allow a user to submit a
complaint, description, and supporting evidence without unnecessarily
collecting personally identifiable information. At the same time, the
system should provide authorized investigators with enough information
to investigate the incident while protecting the reporter's identity.

A major challenge is ensuring that anonymity does not come at the cost
of evidence integrity. Digital evidence can potentially be modified,
deleted, or manipulated after submission. Therefore, the proposed system
can use cryptographic hashing and a hash-chained tamper-evident audit
log to record the integrity of reports and evidence. Each record can be
cryptographically linked to the previous record, making unauthorized
modifications detectable.

Another important aspect is privacy-preserving evidence handling.
Uploaded images, documents, or videos may contain hidden metadata such
as device information, timestamps, GPS coordinates, or software details.
Before storing evidence, the platform can sanitize unnecessary metadata
and encrypt sensitive files. This reduces the possibility of
accidentally exposing information that could identify the reporter.

The system can further incorporate AI-assisted analysis to help
authorized investigators prioritize and organize reports. For example,
submitted reports could be classified by category, urgency, or potential
risk. Similar reports could also be clustered while applying
privacy-preserving techniques to reduce the possibility of identifying
individual reporters.

Key Objectives

1.  Protect reporter anonymity by minimizing collection of personally
    identifiable information.

2.  Secure sensitive reports and evidence through encryption and
    controlled access.

3.  Remove unnecessary metadata from uploaded files to reduce identity
    leakage.

4.  Ensure evidence integrity using cryptographic hashing and
    tamper-evident logs.

5.  Detect unauthorized modifications to submitted reports.

6.  Assist investigators through AI-based classification,
    prioritization, and report clustering.

7.  Build digital trust so users can confidently report sensitive
    incidents without fear of retaliation.

Core Innovation

The project is not simply an anonymous complaint website. Its core
innovation is combining:

Anonymous Reporting + Privacy Protection + Applied Cryptography +
Evidence Integrity + AI Assistance

This makes the platform a privacy-preserving digital trust system for
sensitive reporting.

The strongest demonstration would be:

Submit report → sanitize evidence → encrypt/store it → generate
cryptographic integrity record → attempt to modify the report → system
detects tampering.

Phase 0 — Planning & Scaffolding (1-2 hrs)

-   Finalize data model: Report (id, encrypted_content, category,
    severity, hash, prev_hash, timestamp, status), Evidence (id,
    report_id, sanitized_file_path, file_hash)

-   Set up repo structure: FastAPI backend, Next.js frontend, Docker
    Compose for local orchestration

-   Decide DB: SQLite for speed (Postgres if you want to look more
    "production" — either is fine here, integrity logic matters more
    than DB choice)

-   Pull down Ollama + llama3.2 locally so it's ready when you need
    triage (do this early — model downloads are slow and you don't want
    it blocking you later)

Phase 1 — Secure Report Intake (3-4 hrs)

-   Build the report submission form (Next.js): free-text description,
    category dropdown, optional file upload — no name/email/employee-ID
    fields anywhere

-   FastAPI endpoint to receive submissions, issue a random session
    token (not tied to any identity) so a reporter can check status
    later without logging in

-   No IP logging by default; if you want abuse-prevention, log only a
    salted hash of IP, never raw

Phase 2 — Privacy & Metadata Sanitization Layer (3-4 hrs)

-   On file upload, strip EXIF/GPS/device metadata using Pillow (images)
    or PyPDF2/similar (docs) before anything touches disk

-   Encrypt sanitized files at rest (Fernet/AES via cryptography library
    is fastest to implement correctly)

-   Write a quick before/after test: upload a photo with EXIF GPS data,
    show the stored version has none — this becomes a demo beat

Phase 3 — Tamper-Evident Hash Chain (4-5 hrs, your core differentiator —
give this the most time)

-   On report creation: report_hash = SHA256(report_content +
    evidence_hash + prev_report_hash)

-   Store each report as a link in an append-only chain (no
    UPDATE/DELETE allowed at the DB layer — enforce this in code, not
    just convention)

-   Build a standalone verification script/endpoint that walks the chain
    and confirms every hash matches — this is what you'll run live in
    the demo

-   Test tampering: manually edit a row in the DB, run verification,
    confirm it flags the break at the correct point in the chain

Phase 4 — AI-Assisted Triage (3-4 hrs)

-   Wire up Ollama (reuse your ADAPT LangChain setup) to classify
    incoming reports: category (harassment/corruption/misconduct/other),
    urgency (low/med/high)

-   Optional stretch: simple embedding-based clustering
    (sentence-transformers, runs fine on your 3070 Ti) to group similar
    reports without exposing which reporter filed which — cluster on
    content only, never on metadata that could re-identify

Phase 5 — Investigator Portal (3-4 hrs)

-   Authenticated dashboard (separate from the public reporting form)
    showing: report queue sorted by AI-assigned urgency, category tags,
    chain-integrity status badge per report (✅ verified / ⚠️ tampered)

-   Status-update capability that appends a new chain-linked entry
    rather than mutating the original report (preserves the
    "append-only" story)

-   Basic auth is fine here — investigators aren't the ones needing
    anonymity

Phase 6 — Integration & End-to-End Testing (2-3 hrs)

-   Full flow test: submit → sanitize → encrypt → hash-chain → AI triage
    → appears correctly in investigator dashboard

-   Deliberately break something (edit a DB row) and confirm the whole
    pipeline surfaces it correctly, not just the isolated script

Phase 7 — Demo Polish & Script Rehearsal (2-3 hrs)

-   Rehearse the exact live demo sequence: submit report with photo →

    past record on screen → verification catches it → show AI triage

-   Prepare 1-2 slides on the architecture diagram (you already have a

Here's the full backend and database architecture, with each piece
explained.

Database Schema

sql

-- Reports table: the core anonymous submissions

CREATE TABLE reports (

id INTEGER PRIMARY KEY AUTOINCREMENT,

session_token TEXT NOT NULL, -- random token, NOT tied to identity; lets
reporter check status later

encrypted_content BLOB NOT NULL, -- AES/Fernet-encrypted report text

category TEXT, -- harassment / corruption / misconduct / other
(AI-assigned)

urgency TEXT, -- low / medium / high (AI-assigned)

status TEXT DEFAULT 'submitted', -- submitted / under_review / resolved

report_hash TEXT NOT NULL, -- SHA256(content + evidence_hash +
prev_hash)

prev_hash TEXT, -- hash of the previous report in the chain (NULL for
first ever report)

embedding BLOB, -- stored vector (for clustering similar reports)

created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP

);

-- Evidence table: sanitized files linked to reports

CREATE TABLE evidence (

id INTEGER PRIMARY KEY AUTOINCREMENT,

report_id INTEGER NOT NULL,

sanitized_file_path TEXT NOT NULL, -- path to metadata-stripped,
encrypted file

file_hash TEXT NOT NULL, -- SHA256 of the sanitized file (feeds into
report_hash)

original_metadata_removed TEXT, -- log of what was stripped (for demo
transparency, not sensitive)

uploaded_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

FOREIGN KEY (report_id) REFERENCES reports(id)

);

-- Status updates: append-only log instead of mutating reports directly

CREATE TABLE status_updates (

id INTEGER PRIMARY KEY AUTOINCREMENT,

report_id INTEGER NOT NULL,

new_status TEXT NOT NULL,

updated_by TEXT, -- investigator ID (internal, not reporter-facing)

update_hash TEXT NOT NULL, -- chained the same way as reports, preserves
integrity story

prev_update_hash TEXT,

created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

FOREIGN KEY (report_id) REFERENCES reports(id)

);

-- Investigators: separate from reporters, this is the only table with
real identity

CREATE TABLE investigators (

id INTEGER PRIMARY KEY AUTOINCREMENT,

username TEXT UNIQUE NOT NULL,

password_hash TEXT NOT NULL,

role TEXT DEFAULT 'investigator'

);

Why it's structured this way:

-   reports never stores a name/email/employee-ID — the session_token is
    the only thing linking a submission back to the person who filed it,
    and only they know it

-   prev_hash on both reports and status_updates is what makes the chain
    — each new row cryptographically depends on the one before it, so
    editing history breaks verification

-   status_updates is separate from reports.status being directly
    editable — this is deliberate: investigators never mutate a report
    row, they append a new linked update, which is what lets you
    honestly say "nothing here is ever overwritten"

-   embedding sits on the report row itself so clustering doesn't need a
    separate service call every time

What each service does:

crypto.py — two jobs: (1) encrypts report content before it touches the
DB, decrypts it only when an authenticated investigator pulls it up; (2)
computes SHA256(content + evidence_hash + prev_hash) for chain-linking.
Keep these separate functions so encryption and hashing are
independently testable.

sanitize.py — runs on every file upload before storage.
Uses Pillow's Image.info clearing for images, PyPDF2/pikepdf metadata
stripping for PDFs. Returns both the cleaned file and a hash of it,
which feeds into the report's chain hash.

ai_triage.py — calls your local Ollama instance with a structured
prompt: "Classify this report into one of [categories] and assign
urgency [low/med/high]. Return JSON only." Also generates a
sentence-embedding vector (via sentence-transformers) stored on the
report for later clustering — no training, purely inference calls.

chain_verify.py — the demo centerpiece. Walks every report in order,
recomputes each hash from stored content, and compares it against the
stored report_hash. Returns the first row where they diverge, if any.
This is what you call live when you "break" a record on stage.

                                               investigator-facing dashboard

Flow through the system, end to end:

1.  Report submitted → crypto.py encrypts content → sanitize.py cleans
    any attached file → ai_triage.py classifies + embeds
    → crypto.py computes the chain hash using the previous report's hash
    → row written to reports

2.  Investigator opens dashboard → backend decrypts content on the fly
    for authorized viewing only → sorted by AI-assigned urgency

3.  Status change → new row in status_updates, chained the same way,
    original reports row untouched

4.  Verification → chain_verify.py recomputes every hash in sequence and
    flags the first mismatch

This gives you a clean separation: anonymity logic lives in
how reports is structured (no PII columns, ever), integrity logic lives
entirely in the hash-chain service, and AI is a thin inference layer
that doesn't touch either of those concerns. That separation is also a
good thing to say out loud to judges — it shows the privacy and
integrity guarantees don't depend on the AI working correctly.

Why each piece exists

app/report/ — the entire product exists to make this page trustworthy.
It's deliberately isolated from anything auth-related in the folder
tree, so there's no accidental code path where a submission could get
tied to a logged-in session.

app/report/confirmation/ — separate page (not a modal) so the
session_token is the only thing shown, with nothing else on screen that
could be screenshotted alongside identifying context. Also gives you a
clean demo beat: "here's the token, and that's the only thing that
connects you to this report."

app/status/[token]/ — lets a reporter check on their submission without
ever creating an account. Dynamic route on the token itself keeps this
stateless from your side — you're not maintaining reporter sessions
anywhere.

app/verify/ — a public page, separate from the investigator dashboard,
where anyone (including judges) can trigger the chain-verification check
and watch it work. Keeping this outside /investigator/ means you can
demo integrity without needing to log in on stage, which makes your live
demo faster and less failure-prone.

app/investigator/login/ + /dashboard/ — the only part of the app that
needs real auth. Isolating it under one route lets middleware.ts protect
the whole subtree with one rule instead of guarding pages individually.

app/investigator/dashboard/[id]/ — dedicated detail view per report,
because this is where decrypted content gets shown — you want that
rendering logic in exactly one place, not scattered across a shared card
component that might also render for unauthenticated contexts.

components/report/FileUpload.tsx — its own component (not folded into
ReportForm.tsx) because it needs to show the "metadata stripped ✓"
confirmation after the backend sanitizes the file — that's a distinct
piece of state and UI feedback worth isolating and testing on its own.

components/investigator/IntegrityBadge.tsx — separate from
UrgencyBadge.tsx even though both are small badges, because integrity
status (verified/tampered) and urgency (low/med/high) come from
completely different backend services (hash-chain vs. AI triage) —
keeping them as separate components means a bug in one never touches the
other's rendering logic.

components/investigator/StatusUpdateForm.tsx — deliberately doesn't let
an investigator edit the original report text, only append a new status.
The component's constrained API (it can only call the PATCH /status
endpoint, never PUT /reports) enforces your "nothing is ever
overwritten" guarantee at the UI layer too, not just the backend.

components/verify/ChainVisualizer.tsx — a visual representation of the
hash chain (boxes linked by arrows, with a red break shown when
tampering is detected) — this is worth building as its own component
because it's your single strongest visual for judges; don't bury it
inline in a page file where it's harder to polish.

components/shared/PrivacyNotice.tsx — reusable banner ("We never collect
your name, email, or IP") shown on both the report form and confirmation
page — a shared component ensures the privacy promise is worded
identically everywhere, which matters when judges are evaluating trust.

lib/api.ts — every fetch call to your FastAPI backend goes through here
instead of being scattered in components. This makes it trivial to point
to a different backend URL for demo vs. local dev, and keeps components
free of fetch/error-handling boilerplate.

lib/auth.ts — isolates investigator token storage/refresh logic so it's
the only file in the frontend that ever touches anything
identity-related — easy to point to if someone asks "where does auth
live in your codebase."

lib/types.ts — shared Report, Evidence, StatusUpdate interfaces matching
your backend Pydantic schemas, so the frontend and backend contract
stays in sync as you iterate under time pressure.

middleware.ts — Next.js middleware that checks for a valid investigator
session before allowing any /investigator/* route to render, redirecting
to /investigator/login otherwise. One file, one place to reason about
who can see decrypted report content.
